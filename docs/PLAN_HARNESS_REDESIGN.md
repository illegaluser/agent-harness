# 하네스 전면 재구성 — 방향서

> **이 문서의 지위** — 방향서(Direction)다. 실행 계획이 아니다.
> 무엇을 왜 바꾸는지와 조사로 확인한 사실만 담는다. 단계·파일·완료 조건을 갖춘 실행 계획은
> Architect 가 이 문서를 입력으로 별도 작성하며, 사용자 승인 게이트를 거친 뒤에야 Maker 로 넘어간다.
>
> 작성: 2026-08-02 · 작성자: 오케스트레이터(메인 세션) · 근거: 아래 §2 조사 범위

## 1. 배경 — 왜 재구성인가

사용자 요청은 두 단계였다. 먼저 "현재 하네스의 설계 및 동작 적절성에 대한 객관적 분석이 가능한가",
다음으로 참조 자료(§9)에 기반한 전면 재작성이다.

첫 질문의 답은 **부분적으로 가능**이었다. 내적 정합성과 집행 구조는 기계로 판정 가능하지만,
효과(동작 적절성)는 계측 데이터가 없어 판정 불가다. 이 저장소는
[00-definition.md](../base/docs/harness/00-definition.md) `부록 3` 에서 계측할 지표 4개
(escaped defect rate / rework ratio / cycle time / 토큰per태스크)를 정의해 두고도 넷 다 수집하지 않으며,
같은 절에서 "위 배율은 추정치지 측정값이 아니다"라고 스스로 고지한다.

재구성의 1차 목표는 그래서 **기능 추가가 아니라 집행과 관측의 신설**이다.

## 2. 조사 범위 — 무엇을 확인했고 무엇을 안 봤나

read-only 조사 에이전트 3개를 병렬로 돌려 전수 조사했다.

| 조사 | 범위 | 방법 |
| --- | --- | --- |
| 스펙 지도 | `base/docs/harness/` 4개 파일 1137줄 **전문** | 통독 + 규범 전수 분류 |
| 배포 지도 | `install-harness.sh` · `package-harness.sh` · 훅 2개 · 템플릿 6개 · 설치 문서 3개 **전문** | 통독 |
| 정합성 감사 | 추적 파일 26개 + 설치본(`~/.claude/agents/*.md`, `~/.claude/CLAUDE.md`) | grep·diff 차집합 |

**안 본 것:** 이 저장소를 설치한 다른 프로젝트의 실사용 이력, 런타임 실측(§8 선결 확인 3건).

## 3. 진단

### 3.1 문서가 틀린 게 아니라 집행 계층이 없다

규범(must / must-not) 183개를 집행 주체로 전수 분류한 결과:

| 집행 주체 | 개수 | 실체 |
| --- | --- | --- |
| **RUNTIME** — Claude Code 가 강제 | 약 18 (10%) | 거의 전부 agent frontmatter 의 `tools:` read/write 구분 |
| **ORCHESTRATOR** — 구속 대상이 스스로 집행 | 약 55 (30%) | **게이트 전부** |
| **PROSE** — 아무것도 확인하지 않음 | 약 110 (60%) | 페르소나·사고방식·출력 계약·자가 점검 전부 |

동시에 정합성 감사는 거의 깨끗했다 — 모델 ID 불일치 0건, 역할명 불일치 0건(양방향),
`tools:` 목록 저장소↔설치본 불일치 0건, 섹션 ID dangling 참조 0건.

이 두 결과의 조합이 방향을 결정한다. **전면 재구성은 문서를 다시 쓰는 일이 아니다.**
문서는 내적으로 정합하다. 문제는 183개 규범이 **집행되는 것과 안 되는 것의 구분 없이 전부 같은
문장 형식("~해야 한다")으로** 쓰여 있다는 것이다. 읽는 쪽은 전부 강제되는 줄 알지만 실제로는 10%다.

승인 게이트는 [00-definition.md](../base/docs/harness/00-definition.md) C4 에서
"마커 파일·훅 없이 오케스트레이터가 순서로 보장한다"고 **스스로 비집행 상태임을 명시**한다.

| # | 결함 | 위치 |

| 3 | 권한 allowlist 는 `Bash(markdownlint:*)` 인데 스크립트는 `markdownlint-cli2` 를 호출 — 이름이 달라 권한이 안 걸림 | `base/settings.harness.json:13` vs `base/hooks/lint-gate.sh:100` |

### 3.3 설계된 장치의 다수가 배포 시점에 무력하다

- **글로벌 설치는 훅을 하나도 걸지 않는다.** `merge_settings_json` 이 `scope != "global"` 로 훅 분기
  전체를 막는다(`install-harness.sh:325`). 훅은 프로젝트 설치 전용이다.
- **`inject-repo-facts.sh` 는 모든 신규 설치에서 no-op 다.** 설치 스크립트가 `_repo-facts.md` 를
  만들지 않고, 훅은 그 파일이 없으면 조용히 `exit 0` 한다(`inject-repo-facts.sh:33-35`).
  사람이 수동으로 만들 때까지 SessionStart/SubagentStart 주입은 아무 일도 하지 않는다.
- **`lint-gate` 는 린터 부재 시 inert** — 이건 의도된 설계다. 다만 위 결함 3 때문에 린터가 있어도
  권한에서 걸린다.
- **`VERIFY.md.template` 은 설치되지도 읽히지도 않는다.** 어떤 스크립트도 이 파일을 참조하지 않는다.
- **템플릿 placeholder 가 그대로 배포되고, `--project` 재실행이 사람이 채운 값을 placeholder 로
  되돌린다.** `{{PROJECT_SPECIFIC_TRIGGER_CATEGORIES}}` · `{{DECISIONS_LOG_PATH}}` 가 리터럴로 나간다.
- **`{{DECISIONS_LOG_PATH}}` 오버라이드를 템플릿이 제공하는데 설치 스크립트는 `docs/DECISIONS.md` 를
  하드코딩한다**(`install-harness.sh:763`).
- **설치 영수증·버전 마커가 없다.** 무엇이 어떤 버전으로 설치됐는지 되짚을 방법이 없어 uninstall 이
  원리적으로 부정확하다 — `base/INSTALL.md:88-96` 이 이 손실을 자인한다.

### 3.4 정본이 정본이 아니다

| 파일 | 저장소 | 설치본 (`~/.claude`) | 차이 |
| --- | --- | --- | --- |
| `critic.md` | 120줄 | 143줄 | **+23** — 교차 참조 정합 절 |
| `maker.md` | 183줄 | 203줄 | **+20** — 블록 교체 정보 유실 확인 절 |
| `CLAUDE.harness-global.md` | 128줄 | 153줄 | **+25** — 토큰 규율의 예외 2건 |

저장소에서 삭제된 줄 0, 설치본에만 있는 줄 68. 즉 **설치본이 저장소보다 앞서 있다.**
`README.md:47` 은 이 저장소를 "단일 정본"이라 선언한다. 역류(backflow) 경로가 없어서 생긴 구조 결함이다.

## 4. 재구성 축 — 4계층

참조 자료의 4계층(선언 / 역할 배정 / 모델 리매핑 / 강제)을 이 하네스에 맞게 재정의한다.

| 층 | 이름 | 현재 상태 | 재구성 후 |
| --- | --- | --- | --- |
| **L1** | 선언 — 규범 텍스트 | 2596줄, 집행 여부 구분 없음 | 코어/플레이북 분리 + 규범마다 집행 계층 표기 |
| **L2** | 배역 — agent frontmatter | **유일하게 작동 중** | 유지 + 모델 세대 갱신 + 결함 1 수정 |
| **L3** | 집행 — 훅 | 사실상 없음 (lint 하나, 그나마 inert) | write-gate · close-gate 신설 |
| **L4** | 관측 — 계측·영수증·검증 | **0** | 전부 신설 |

## 5. 재구성 원칙 4개

### 원칙 1 — 규범은 자기가 집행되는 층에 산다

각 규범을 재배치한다. 기계로 판정 가능하면 L3 훅으로, frontmatter 로 표현 가능하면 L2 로,
사람·모델의 판단이 필요하면 L1 에 남긴다.

**L1 에 남는 규범에는 "이 규칙은 집행되지 않는다"를 명시한다.** 지금처럼 집행되는 규칙과 아닌 규칙을
같은 어조로 뭉뚱그리지 않는다.

- **금지 예:** 집행 수단이 없는 규칙을 "~해야 한다"로만 적고 끝낸다.
- **허용 예:** 규칙 옆에 집행 계층을 표기하고, 비집행이면 그렇다고 적는다.

### 원칙 2 — 상시 주입 텍스트와 온디맨드 텍스트를 가른다

코어에는 **첫 토큰부터 참이어야 하는 것만** 담는다 — 불변식 3개, 파이프라인 발동/스킵 조건,
커밋 규약, 게이트 문턱. 오케스트레이션 패턴표·검증 등급표·역할별 상세는 온디맨드로 뺀다.
근거: 코어는 매 세션 시작마다 전량 지불된다.

### 원칙 3 — 산출물의 정의를 프로젝트가 선언한다

참조 자료의 게이트는 코드 확장자 목록을 하드코딩하고 마크다운·JSON 을 명시적으로 통과시킨다.
그 전제가 이 저장소에서는 뒤집힌다. 추적 파일 26개의 실측 구성:

```text
16 md · 4 sh · 3 template · 2 json · 1 gitignore
```

`.py` / `.ts` / `.go` 0개다. 확장자 기준 게이트는 `.sh` 4개만 잡고, 이 하네스의 실제 산출물인
md 16개와 template 3개를 전부 통과시킨다. 따라서 **게이트 대상 집합은 프로젝트가 선언하는 설정**이어야
한다. 이 저장소에서는 `base/**` 와 `docs/**`, 코드 프로젝트에서는 코드 확장자.

### 원칙 4 — 정본은 하나이고 역류 경로가 있다

§3.4 의 68줄 드리프트는 사고가 아니라 구조 결함이다. 설치본을 고치면 저장소로 돌아올 길이 없다.
최소한 drift 검출 경로(`--check` 모드 등)가 있어야 하고, 설치 영수증(§6 L4)이 그 근거가 된다.

## 6. 층별 구현 방향

### L3 집행 — 신설

**write-gate** — `PreToolUse` 훅, 대상 `Write|Edit|NotebookEdit|Bash`.

- 훅 페이로드의 `agent_id` / `agent_type` 필드 유무로 메인 세션과 서브에이전트를 가른다.
  서브에이전트(=Maker)는 통과, 메인 세션은 산출물 파일 개수를 제한한다.
  이것이 불변식 1("write 는 오직 Maker 만")을 처음으로 기계 집행 가능하게 만드는 수단이다.
- **문턱은 자작 숫자가 아니라 기존 스펙에서 유도한다.** 하네스는 이미 같은 경계를 두 곳에서 정해 뒀다 —
  스킵 조건의 "1~2 개 파일" 과 Maker 경계의 "3 개 파일 이상이면 계획 필요". 게이트는 이 두 문장을
  기계로 옮긴 것이지 새 숫자를 도입하는 것이 아니다. 차단 메시지도 "위임하라"가 아니라
  스펙 문언 그대로 "3 개 파일 이상 — Architect 계획이 필요하다"여야 한다.
- 대상 집합은 원칙 3 에 따라 프로젝트 설정에서 읽는다.
- `docs/DECISIONS.md` append 는 예외다 — 00-definition C4 가 이미 명문화한 예외를 그대로 옮긴다.
- Bash 우회 경로(`sed -i` · `perl -i` · 리다이렉트 · `tee`)를 차단한다. 현재 불변식 1 은 Bash 한 줄로
  무력화된다.
- **fail-open** — 게이트 자체 오류 시 차단이 아니라 통과. `lint-gate.sh` 의 self-degrade 와 같은 철학이며
  선례가 이미 저장소 안에 있다.
- **선결 제약:** 참조 자료는 턴 경계 감지에 쓰는 `prompt_id` 가 Claude Code v2.1.196 이상에서 제공된다고
  명시한다. 이 머신은 설계 시점에 `2.1.128` 로 미달이었다(**2026-08-03 `2.1.220` 으로 해소**).
  업그레이드가 불가했다면 턴당 카운터가 아니라
  **세션당 카운터 + Stop 훅 리셋**으로 설계를 바꾼다. 시간창 기반 대안은 또 다른 자작 문턱을 낳으므로 쓰지 않는다.

**close-gate** — `Stop` / `SubagentStop` 훅.

- 열린 요구사항 항목이 남은 채 턴이 끝나는 것을 차단한다. 불변식 3("게이트 없는 상태 전이는 없다")이
  현재 종료 시점에서 전혀 집행되지 않는 것을 메운다.
- `lint-gate.sh` 의 유한 차단 패턴(`MAX_BLOCKS=3`, 클린 시 카운터 리셋)을 그대로 재사용한다.
  세션이 영구히 막히지 않게 하는 상한이 이미 검증돼 있다.

### L4 관측 — 신설

- **계측** — 모든 훅이 `.claude/state/` 아래 `*.jsonl` 에 이벤트 한 줄을 append 한다.
  **프롬프트 내용은 절대 기록하지 않는다.** 이벤트만 남긴다.
  [00-definition.md](../base/docs/harness/00-definition.md) `부록 3` 이 이미 정의해 둔 지표 4개를 살린다.
- **설치 영수증** — 설치 시 버전·파일 해시·설치 시각을 남긴다. §3.3 의 uninstall 부정확성과
  §3.4 의 drift 검출을 동시에 해결한다.
- **검증 자동화** — `VERIFY.md` 를 실제로 설치하고, 참조 자료의 2단 검증을 헤드리스 세션으로 자동화한다.
  게이트는 **차단이 걸리는 것**과 **서브에이전트는 통과하는 것**이 함께 확인돼야 완성이다.
  하나만 확인하면 각각 "무용한 게이트" 와 "오케스트레이션 마비" 를 못 잡는다.
  이 저장소에는 현재 테스트가 0개다.

### L2 배역

- `architect.md` 의 `claude-opus-4-8` 은 현행 세대보다 뒤처져 있다. 되돌리기 비용이 큰 판단을
  구세대 모델에 맡기는 상태이므로 갱신 대상이다.
- §3.2 결함 1(R7 요약표 모순) 수정.
- `reasoning_effort` 키의 유효성 확인 — §8 선결 확인 참조.

### L1 선언

- 코어 / 온디맨드 분리 (원칙 2).
- 규범마다 집행 계층 표기 (원칙 1).
- §3.3 배포 결함 수정 — placeholder 되돌림, `{{DECISIONS_LOG_PATH}}` 하드코딩, no-op 훅,
  권한 이름 불일치.
- §3.2 결함 2·4 수정.

| **1** | L4 관측 | **먼저 재야 문턱을 근거로 정한다.** 안 그러면 전역 규율이 금지한 "근거 없는 자작 숫자 문턱"이 된다 |
| **2** | L3 집행 | 관측 데이터 위에서 문턱을 확정 |
| **3** | L1 재구성 | 집행 계층이 정해져야 어떤 규범이 어디로 갈지 결정된다 |
| **4** | 배포 정리 + 역류 경로 | 위 셋을 실제로 배달 가능하게 만든다 |

## 8. 미확인 — 선결 확인 3건

아래 셋은 조사로 확인하지 못했다. **L3 설계가 이 결과에 의존하므로 Architect 착수 전에 해소한다.**

1. **`reasoning_effort` 인가 `effort` 인가.** 저장소와 설치본은 전부 `reasoning_effort` 를 쓰고
   두 곳이 일치한다(불일치 0건). 참조 자료는 `effort:` 를 쓴다. 한쪽은 무시되고 있을 수 있으며,
   **조용히 실패하는 종류**라 위험하다. 무시되고 있다면 지금 모든 역할이 의도한 추론 예산으로 돌지 않는다.
2. ~~**Claude Code 업그레이드 가능 여부.** 현재 `2.1.128`, 참조 자료가 `prompt_id` 요구 버전으로 명시한
   값은 `2.1.196`. 불가하면 write-gate 를 세션 단위 설계로 전환한다.~~
   **해소 (2026-08-03).** `2.1.220` 설치 완료. 라이브 카운터에서 `turn` 이 실제 UUID로 기록되는 것을
   확인했다 — `turn_key()` 가 값을 돌려주므로 턴당 카운터 설계가 그대로 선다. 세션 단위 전환은 불필요.
3. **`agent_id` 실측.** 참조 자료가 기술한 대로 서브에이전트의 `PreToolUse` 페이로드에 `agent_id` /
   `agent_type` 이 실제로 실리는지, 메인 세션에는 없는지 확인한다. 이 필드가 없으면 write-gate 의
   메인/서브 판별 근거 자체가 사라지므로 **설계 전제**다.

## 11. 이 문서의 한계

1. **작성자가 평가 대상의 운용 당사자다.** 이 하네스의 불변식 2 는 "자기 산출물을 자기가 최종
   검증하지 않는다"이며, 전역 규율은 "증거는 산출물이지 자기 보고가 아니다"라고 못박는다.
   §3 의 진단은 **판정이 아니라 발견 목록**이다. 조사는 read-only 서브에이전트 3개가 수행했으나
   종합은 오케스트레이터가 했다.
2. **효과에 대한 주장은 하나도 담지 않았다.** 재구성이 품질을 올린다는 근거는 현재 없다.
   그 근거를 만드는 것이 단계 1(L4 관측)의 목적이다.
3. **§8 이 미해소인 상태에서 L3 을 설계하면 안 된다.**
