# 하네스 설치·삭제 가이드 (초보자용)

이 문서는 개발자가 아니어도 따라 할 수 있게 "멀티 에이전트 하네스"를 설치하고, 필요하면 다시
지우는 방법을 설명한다. 명령을 그대로 복사해서 실행하면 되도록 구성했다. 더 압축된 안내가
필요하면 [`INSTALL.md`](INSTALL.md)를, 하네스의 정식 스펙이 궁금하면
[`base/docs/harness/00-definition.md`](base/docs/harness/00-definition.md)부터 읽는다(아래 "더
알아보기" 참고).

## 1. 하네스가 뭔가요

AI 코딩 도구(Claude Code) 혼자에게 "이거 만들어줘"라고 맡기면, 조사도 하고 설계도 하고 코드도
쓰고 검증도 하는 걸 한 명이 다 한다. 사람 조직으로 치면 한 사람이 기획·설계·시공·감리를 전부
겸하는 셈이라, 바쁠수록 검증이 대충 넘어가기 쉽다.

이 하네스는 그 한 명을 **역할이 나뉜 작은 팀**으로 바꾼다. 팀원은 다섯이다.

| 역할 | 하는 일 (한 줄) |
| --- | --- |
| scout (조사자) | 코드와 문서를 뒤져서 "지금 뭐가 있는지" 사실만 보고한다. 판단은 안 한다. |
| architect (설계자) | scout의 사실 지도를 보고 "어떻게 바꿀지" 계획서를 그린다. 코드는 안 쓴다. |
| maker (시공자) | 승인된 계획서대로 실제로 코드를 바꾼다. 이 팀에서 파일을 쓰는 건 이 역할뿐이다. |
| critic (검증자) | maker가 바꾼 걸 보고 문제가 있는지 찾아 합격/조건부/불합격을 판정한다. |
| referee (심판) | 여러 검증 결과가 동시에 나올 때(팬아웃) 그걸 하나로 종합한다. |

핵심 규칙 하나만 기억하면 된다 — **maker가 아닌 역할은 파일을 고치지 못하고, maker가 만든 변경은
critic(자기 자신이 아닌 다른 역할)이 검증한다.** 그래서 "만든 사람이 자기 채점까지 하는" 사고가
구조적으로 막힌다.

이걸 도와주는 자동 장치(훅) 2개가 있다.

- **사실 자동 주입**: 세션을 시작할 때마다 이 저장소의 포트·경로 같은 고정 사실을
  (`_repo-facts.md`) 자동으로 대화에 끼워 넣어준다 — 매번 다시 설명 안 해도 된다.
- **lint(코드 검사) 점검**: 방금 고친 파이썬/마크다운 파일에 흔한 실수(문법 오류, 마크다운 규칙
  위반 등)가 있으면 알려준다.

"계획서가 아직 사용자 승인을 못 받았는데 코드부터 쓰려는" 시도는 훅이 아니라 Claude Code 자체의
승인 팝업(ExitPlanMode)과, architect의 계획을 사용자가 승인하기 전에는 maker를 부르지 않는
진행 순서로 막는다(아래 FAQ 참고).

그리고 `docs/DECISIONS.md`라는 **결정 로그**가 있다 — "이 프로젝트에서 왜 이렇게 하기로
했는지"를 계속 쌓아두는 기록장이다. 나중에 "이거 왜 이렇게 돼 있지?"란 질문에 답할 때 쓴다.

## 2. 설치 전 준비물

| 준비물 | 필수 여부 | 없으면 |
| --- | --- | --- |
| Claude Code (훅을 지원하는 버전) | 필수 | 하네스 자체가 동작하지 않는다 |
| bash | 필수 | 인스톨러(`install-harness.sh`)를 실행할 수 없다 |
| python3 | 필수 | 인스톨러 내부 병합 로직이 python3 로 작성돼 있다 |
| git | 필수 (`--project` 설치 시) | 설치 대상 경로가 진짜 저장소 루트인지 확인하지 못한다 |
| ruff / markdownlint-cli2 | 선택 | 없어도 설치는 똑같이 된다. 다만 lint 점검 훅이 "할 일이 없다"며 조용히 쉰다(아래 FAQ 참고) |

네트워크 접속은 필요 없다. 이 하네스는 **폐쇄망(인터넷이 안 되는 환경) 을 기본 전제로
설계**됐다 — 압축 파일 하나만 옮기면 그 안에서 다 끝난다.

## 3. 설치하기

설치 방식은 두 가지다. 필요에 따라 하나만 골라도 되고, 둘 다 해도 된다.

| 방식 | 명령 | 무엇이 어디에 깔리나 |
| --- | --- | --- |
| 글로벌(내 컴퓨터 전체, 한 번만) | `bash install-harness.sh --global` | `~/.claude/` 아래에 에이전트 5개(`agents/*.md`)·규칙(`CLAUDE.md`)·권한 설정만. **훅은 깔리지 않는다.** |
| 프로젝트(저장소마다) | `bash install-harness.sh --project <저장소경로>` | 그 저장소의 `.claude/`, `docs/` 아래에 스펙 문서·훅 2개·상태 폴더·결정 로그 시드까지 |

**중요 — 훅은 `--project`에서만 배선된다.** `--global`은 "역할 정의와 규칙"만 내 컴퓨터 전체에
깔아 두는 것이고, 자동 차단·자동 주입 같은 실제 동작(훅)은 프로젝트별로 `--project`를 따로
실행해야 그 저장소에 배선된다. 두 명령이 하는 일이 다르므로, 실제로 하네스가 "동작"하길
원한다면 최소한 그 저장소에는 `--project`를 실행해야 한다.

### 3-1. 실행권한이 없다는 오류가 나면

```bash
chmod +x install-harness.sh
```

`install-harness.sh`에 실행 권한을 부여한다. 압축을 푸는 도구에 따라 실행권한이 날아가는 경우가
있어서 필요할 수 있다.

### 3-2. 미리보기 — `--dry-run`

실제로 아무것도 바꾸지 않고, 무엇을 만들지·건드릴지만 화면에 출력해준다. 처음 써보는
저장소라면 먼저 이걸로 확인해보는 걸 권장한다.

```bash
bash install-harness.sh --project /path/to/target-repo --dry-run
```

### 3-3. 기존 설정을 덮어쓰지 않는다는 안심 포인트

이미 그 컴퓨터/저장소에 `settings.json`이나 `CLAUDE.md`가 있어도 걱정할 필요 없다.

- `settings.json`은 기존 내용을 지우지 않고 **병합**한다(권한·훅 항목을 더할 뿐).
- `CLAUDE.md`는 `<!-- HARNESS:BEGIN -->` ~ `<!-- HARNESS:END -->` 표시가 있는 구간만 갱신하고,
  그 바깥의 기존 글은 그대로 둔다.
- 에이전트 파일 같은 것을 사람이 이미 손으로 고쳐놨다면(=배포본과 내용이 다르면), 설치는 그걸
  덮어쓰지 않고 "커스터마이즈된 것 같아 건너뜁니다"라고 경고만 하고 넘어간다. 정말 덮어쓰고
  싶으면 `--force`를 추가한다(그래도 먼저 `.bak-<시각>` 백업을 남긴 뒤에 덮어쓴다).

## 4. 설치 후 할 일

설치 스크립트가 자동으로 채우지 못하는 두 가지가 있다 — 그 프로젝트를 실제로 아는 사람만
채울 수 있는 정보이기 때문이다.

1. **`_repo-facts.md` 만들고 채우기**: 설치 스크립트는 이 파일을 자동으로 만들지 않는다 — 그
   저장소를 모르는 채로 사실을 지어내는 셈이 되기 때문이다. 먼저 템플릿을 대상 저장소의 정해진
   자리로 복사한다(번들 최상위에서 실행). `.claude/agents/` 폴더가 아직 없는 저장소도 많으므로,
   복사 전에 `mkdir -p`로 그 폴더부터 만들어 둔다.

   ```bash
   mkdir -p /path/to/target-repo/.claude/agents
   cp base/templates/_repo-facts.md.template /path/to/target-repo/.claude/agents/_repo-facts.md
   ```

   그런 다음 복사된 `<repo>/.claude/agents/_repo-facts.md` 파일을 열어, 그 저장소의 실제 포트
   번호·실행 명령(launcher)·토폴로지 같은 §1~§8 자리표시자를 실제 값으로 바꿔 넣는다.
2. **Claude Code에서 확인하기**: 새 Claude Code 세션을 열고 `/agents`를 실행해 scout / architect /
   maker / critic / referee 다섯 역할이 목록에 보이는지 확인한다.

## 5. 삭제하기

```bash
bash install-harness.sh --uninstall --global
bash install-harness.sh --uninstall --project /path/to/target-repo
```

각각 다음을 지운다.

- `--uninstall --global`: 설치 때 깔았던 에이전트 파일들을 지우고(배포본과 완전히 같을 때만 —
  손으로 고친 흔적이 있으면 지우지 않고 경고만 한다), `settings.json`·`CLAUDE.md`에서 하네스가
  추가했던 부분만 도로 뺀다.
- `--uninstall --project`: 스펙 문서·훅 2개·`docs/DECISIONS.md` 시드·상태 폴더를 같은 방식으로
  지우고, `settings.json`·`CLAUDE.md`에서 하네스 관련 부분만 뺀다.

**되돌아가는 법**: 삭제(또는 덮어쓰기) 직전에는 항상 `<파일명>.bak-<시각>-<프로세스번호>` 형태의
백업이 자동으로 만들어진다. 뭔가 잘못됐다 싶으면 그 백업 파일을 원래 이름으로 복사해 되돌리면
된다. 삭제 명령은 이 백업 파일 자체는 절대 건드리지 않으므로, 필요하면 나중에 수동으로 정리한다.

**빈 폴더가 남을 수 있다**: 삭제 후에도 `.claude/hooks/`나 `docs/harness/` 같은 빈 폴더가 남을 수
있다. 안에 파일이 없다면 무해하니 그냥 둬도 되고, 신경 쓰인다면 직접 지워도 된다.

## 6. 자주 묻는 것(FAQ)

**Q. 글로벌로 설치했는데 훅(자동 차단/자동 주입)이 안 도는 것 같아요.**
정상이다. `--global`은 원래 훅을 설치하지 않는다(§3 참고). 훅이 실제로 동작하길 원하는
저장소에는 그 저장소를 대상으로 `--project <저장소경로>`를 따로 실행해야 한다.

**Q. lint 점검 훅이 아무것도 안 하는 것 같아요.**
`ruff`나 `markdownlint-cli2`가 그 컴퓨터에 설치돼 있지 않으면, lint 점검 훅은 "검사할 도구가
없다"며 조용히 통과(self-degrade)한다. 오류가 아니라 설계된 동작이다 — 두 도구를 설치하면 다시
검사가 동작한다.

**Q. Architect가 짠 계획을 승인했다는 표시를 어떻게 남기나요?**
별도 마커 파일을 만들 필요가 없다. Claude Code가 Plan Mode일 때 architect의 계획서를 다 읽고 나면
화면에 **승인/거절을 묻는 팝업(ExitPlanMode)**이 뜬다 — 여기서 "승인"을 누르는 것 자체가 승인
표시다. (팝업이 안 뜨는 경우엔 사람이 대화창에 "승인합니다" 같은 말로 명시적으로 답해도 된다.)
그 승인이 있기 전까지, 세션을 이끄는 쪽(오케스트레이터)은 maker를 부르지 않는다 — 즉 "승인 전에는
코드를 쓸 사람 자체가 등장하지 않는" 방식으로 순서가 지켜진다. 승인 마커 파일이나 우회용 환경변수는
더 이상 없다.

**Q. `settings.json`이 이미 손상돼(문법이 깨져) 있으면 설치·삭제가 위험한가요?**
아니다. 설치·삭제 스크립트는 대상 파일을 병합/역병합하기 **전에** 먼저 유효한 JSON인지
확인한다. 깨져 있으면 아예 손대지 않고 "건드리지 않고 건너뜀"이라는 경고만 남긴 뒤 나머지
작업(에이전트 파일, 문서 등)을 계속 진행한다 — 망가진 파일을 잘못 "복구"한답시고 더 망치는
일은 없다.
