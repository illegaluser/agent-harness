# 멀티 에이전트 하네스 — 정의

> **하네스** = 에이전트(모델)를 감싸, 작업을 **수행·검증·재현 가능**하게 만드는 실행 골격.
> **경계** = 요구 이해부터 릴리스 노트 작성까지. 실제 배포·운영은 밖.
> **우선순위** = ① 품질/검증 ② 역할 분리/재현성 ③ 컨텍스트 확장. (병렬 처리량은 부산물이지 목표가 아니다.)

이 문서는 **"무엇인가(개념·역할·절차)"** 만 정의한다. 실제 프롬프트·스크립트는 후속 문서(`01-roles.md`, `02-orchestration.md`)에서 다룬다.

---

## Part A · 개념

### A1. 하네스란 무엇인가

단일 에이전트 한 세션은 세 한계에 부딪힌다. 하네스는 이 셋을 **더 똑똑한 모델이 아니라 구조로** 푼다.

| 단일 세션의 한계 | 하네스의 해법 |
| --- | --- |
| **자기 검증 불가** — 자기 출력을 자기가 채점하면 결함을 계속 놓친다 | 만드는 역할과 검증하는 역할을 분리 |
| **역할 혼재** — 계획·구현·판정이 섞이면 근거 추적·재현이 안 된다 | 역할마다 책임·권한·경계를 고정 |
| **컨텍스트 한계** — 한 컨텍스트에 안 들어가는 작업은 시작조차 못 한다 | 작업을 쪼개 여러 인스턴스에 분산 |

### A2. 두 개의 경계

하네스는 **무엇으로 이루어지나(기계 경계)** 와 **무슨 일까지 하나(작업 경계)** 를 각각 못 박는다.

#### ① 기계 경계 — 하네스를 구성하는 것

| 안 | 밖 |
| --- | --- |
| 역할·권한·순서·게이트·메모리·계약(schema) | 모델의 가중치·추론 능력 |
| = 하네스가 *설계·통제*하는 것 | = 하네스가 *못 바꾸고, 잘 쓰기만* 하는 것 |

#### ② 작업 경계 — 하네스가 처리하는 SDLC 범위

기준은 공정 이름이 아니라 **인지 vs 실행**이다.

| 안 = 인지작업 | 밖 = 실행작업(actuation) |
| --- | --- |
| 가역 · 리뷰가능 산출물 · 재현가능 | 비가역 · 외부발신 · 사람/도구 소유 |
| 요구 이해 → 조사 → 설계 → 구현 → 테스트 → **릴리스 노트·changelog·PR 조립** | 실제 배포·롤백·페이징·트래픽 조작·모니터링·장애대응 *실행* |

**경계선 = 릴리스 아티팩트 산출 지점.** 하네스는 배포 가능한 릴리스 노트/PR을 내놓고 손을 뗀다. 그 뒤는 seam(이음매)으로만 위임한다.

> **왜 여기서 끊나** — 배포 이후는 하네스가 지키기로 한 가치(재현성·가역성)를 원천적으로 못 지킨다. 프로덕션은 움직이는 표적이라 재현 불가, 배포는 비가역. read-only/write 분리라는 안전 모델이 성립하지 않는다.
> **예외** — 배포·운영의 *분석* 인지작업(장애 원인 가설, 로그 상관 → 보고서)은 에이전트가 잘한다. 단 dev 파이프라인의 연장이 아니라, 프로덕션 텔레메트리를 향한 **별개의 read-only 하네스**로 둔다.

### A3. 5층 모델

하네스는 5개 층으로 분해된다. **프로젝트 도입 = 이 5층을 글로벌 기본값 + 프로젝트 오버라이드로 채우는 일.** 각 층은 우선순위 가치 중 하나 이상을 책임진다.

| 층 | 정의 | 지키는 가치 | 본문 |
| --- | --- | --- | --- |
| **L1 역할** | 각 에이전트의 책임·권한·경계 | 역할 분리 | Part B |
| **L2 오케스트레이션** | 역할을 잇는 순서·패턴 | 컨텍스트 확장 · 재현성 | C1–C2 |
| **L3 계약** | 에이전트 간 데이터의 형태(schema) | 재현성 · 품질 | C3 |
| **L4 게이트** | 다음 단계로 넘어갈 통과 조건 | 품질/검증 | C4 |
| **L5 메모리** | 세션·에이전트 간 지속 상태 | 컨텍스트 확장 · 재현성 | C5 |

> **판정 규칙**: 어떤 하네스든 이 5층으로 남김없이 설명되지 않으면, 정의가 덜 된 것이다.

## Part B · 역할 (L1)

역할은 "직업"이 아니라 **책임 + 입출력 + 권한 + 경계**의 묶음이다. 특정 이름(planner 등)이 아니라 **원형(Archetype)** 으로 정의하고, 실제 에이전트는 원형의 인스턴스다.

### B1. 역할 정의 템플릿

모든 역할은 반드시 이 5칸을 채운다. 하나라도 비면 역할 정의가 아니다.

- **책임** — 산출하는 단 하나의 결과물
- **입력 ←** — 무엇을 받아서
- **출력 →** — 무엇을 내놓나 (= 책임의 구체형)
- **권한** — 만질 수 있는 도구. 특히 **read-only vs write** 를 못 박는다
- **경계** — 절대 하지 않는 것. 위반 시 즉시 멈춘다

### B2. 다섯 원형

표를 **파이프라인 순서**로 읽으면 `입력→출력`이 사슬처럼 이어진다.

| 원형 | 입력 ← | 출력 → (책임) | 권한 | 경계 |
| --- | --- | --- | --- | --- |
| **Scout** | 요구·질문 | 사실 지도 | read-only | 판단·수정 금지. 찾기만 한다 |
| **Architect** | 사실 지도 | 실행 계획 | read-only | 코드 작성 금지 |
| **Maker** | 승인된 계획 | 코드 변경 | **read/write** | 계획 없이 시작 금지 |
| **Critic** | 코드 변경 | 결함·판정 보고 | read-only | 수정 금지. 발견·판정만 |
| **Referee** | 여러 결과 | 종합·채점 | read-only | 새 작업 생성 금지. 고르고 합칠 뿐 |

> **재현성의 핵심** — Maker 하나만 세계를 바꾼다(write). 나머지 넷은 부작용이 없어(read-only), 같은 세계에서 몇 번을 돌려도 같은 지점에서 출발한다. **이 write 단일화가 재현성을 보장한다.**

## Part C · 절차와 규칙

### C1. 기본 파이프라인

기본형은 **순차 + 게이트**다. 재현성이 가장 높다.

```text
  Scout ──▶ Architect ──▶〔승인 게이트〕──▶ Maker ──▶ Critic ──▶〔검증 게이트〕
  조사       계획          사용자 승인        구현       판정        PASS/재호출
  (RO)      (RO)                            (RW)      (RO)
```

- 게이트를 통과하지 못하면 다음 역할로 넘어가지 못한다 (→ C4).
- Referee는 이 사슬에 상주하지 않는다. 아래 팬아웃/분할 패턴에서만 등장한다.

### C2. 오케스트레이션 패턴 (L2)

기본 파이프라인을 확장하는 4개 패턴. **병렬은 목적이 아니라 수단**이다 — "빠르니까"가 아니라 "독립 관점이 결함을 더 잡으니까(품질)" 또는 "한 컨텍스트에 안 들어가니까(확장)" 쓴다.

| 패턴 | 구성 | 언제 |
| --- | --- | --- |
| **순차 게이트** | Scout→Architect→Maker→Critic (C1) | 기본형. 재현성 최우선 |
| **팬아웃-검증** | N개 Critic이 독립 채점 → 다수결 | 코드 변경 기본 검증(품질) |
| **분할-정복** | 작업 분할 → Maker N개 → Referee 종합 | 컨텍스트를 넘길 때 |
| **적대적 검증** | Critic에게 "이 결과를 *반증*하라" | 품질의 최후 방어선 |

### C3. 계약 (L3)

에이전트 간 전달은 **자유 서술이 아니라 정해진 형태**여야 재현·검증된다.

- **핸드오프 계약** — 원형 간(Scout→Architect 등) 넘기는 산출물의 필수 필드를 고정한다.
- **판정 계약** — Critic/Referee 출력은 반드시 `{판정, 근거, 재현경로}` 형태. "좋아 보임" 금지.
- **판정 값** — 최소 `PASS / CONDITIONAL / FAIL` 3값. CONDITIONAL은 경고 목록을 동반한다.

### C4. 게이트와 불변식 (L4)

**게이트 = 통과 못 하면 다음 단계로 못 가는 조건.** 품질은 "잘하자"가 아니라 게이트로 강제된다.

- **승인 게이트** — Architect의 계획은 사용자 명시 승인 없이 Maker로 못 넘어간다. 집행: 네이티브 승인 표면(Claude Code Plan Mode/ExitPlanMode, 메인 세션) + 오케스트레이터 시퀀싱(승인 전 Maker 미소환). 마커 파일·훅 없이 오케스트레이터가 순서로 보장한다.
- **검증 게이트** — Critic이 FAIL이면 Maker 재호출(최대 N회). 초과 시 사용자 에스컬레이션.

**불변식 — 언제나 참이어야 한다:**

1. write는 오직 Maker만 한다. **예외** — 오케스트레이터의 `docs/DECISIONS.md` append(02-orchestration O0). 작업 산출물(코드·설정 변경)이 아니라 하네스 자체의 감사 로그라 명시적으로 예외 처리한다. append만 허용되고 기존 항목 edit는 이 예외에 포함되지 않는다.
2. 자기 산출물을 자기가 최종 검증하지 않는다 (Maker ≠ Critic).
3. 게이트 없는 상태 전이는 없다.

### C5. 메모리 (L5)

- **세션 메모리** — 프로젝트 목표·제약·결정 (`~/.claude/.../memory/`).
- **작업 메모리** — 팬아웃/분할 시 에이전트가 공유하는 중간 상태. 재현을 위해 로그로 남긴다.
- **원칙** — 코드·git 이력으로 복원 가능한 것은 넣지 않는다. *비자명한 것만.*

### C6. 의사결정 로그 (Decision Log)

게이트(L4)는 결정이 확정되는 지점이다. 그 결정을 **append-only 로그**로 영속화해, "왜 그때 그렇게 정했나"를 추적 가능하게 만든다. 승인·검증 게이트의 결과가 여기 쌓인다(작동·스키마는 02-orchestration O0).

- **메모리(L5)와 다르다** — 메모리는 덮어쓰는 "최신 사실", 결정 로그는 지워지지 않는 "왜의 이력". 그래서 메모리에 넣지 않고 별도 아티팩트로 둔다.
- **위치** — 프로젝트당 단일 누적 파일(기본 `docs/DECISIONS.md`). Docs-First가 읽는 결정 소스(ADR과 같은 계열).
- **작성 주체의 정의는 여기(B2 5원형)에 없다** — 로그를 쓰는 오케스트레이터의 책임·입력·출력·권한·경계(B1 5칸)는 [`02-orchestration.md`](02-orchestration.md) O0에 정의한다. 게이트 종료 조건인 `DECISION_LOG` 강제 마커 문법도 그곳에 있다.

## 부록 1. 기존 3-에이전트 매핑

백지 재정의가 기존 파이프라인을 포괄하는지 확인:

| 기존 | 원형 |
| --- | --- |
| `planner` | Architect |
| `implementer` | Maker |
| `verifier` | Critic |
| — (신규) | Scout, Referee — 컨텍스트 확장·다중 결과 종합용 |

→ 기존 파이프라인은 이 정의의 **부분집합**이다. 하위 호환된다.

## 부록 2. 용어

| 용어 | 뜻 |
| --- | --- |
| **하네스 (Harness)** | 모델을 감싸는 실행 골격 전체 |
| **층 (Layer, L1–L5)** | 하네스의 구성 부품 축 |
| **원형 (Archetype)** | 이름에 묶이지 않는 역할의 정의 단위 |
| **패턴 (Pattern)** | 원형을 잇는 오케스트레이션 방식 |
| **게이트 (Gate)** | 상태 전이의 통과 조건 |
| **불변식 (Invariant)** | 언제나 참이어야 하는 규칙 |
| **seam (이음매)** | 하네스 밖 시스템과의 위임 접점 |

## 부록 3. 기대 효과와 측정

이 루프는 **속도(wall-clock) 장치가 아니라 재작업 제거 장치**다. 기대값은 "빨라진다"가 아니라 "덜 틀리고·덜 고치고·더 큰 걸 시작할 수 있다"로 잡는다.

### 두 종류의 효율 구분

| | 정의 | 이 루프의 영향 |
| --- | --- | --- |
| **원(raw) 속도** | 태스크 하나 시작→끝 벽시계 시간 | **악화** — 게이트·계획·검증 오버헤드로 1.2~2배 느려짐 |
| **유효(effective) 처리량** | 재작업·되돌림·QA 반려를 뺀 실질 산출 | **개선** — 값은 여기서 나온다 |

### 관점별 기대 (적합한 태스크 한정)

| 관점 | 지표 | 방향·대략치 |
| --- | --- | --- |
| 개발자 | 코드 작성 속도 | ≈ 또는 소폭 악화 (게이트 오버헤드) |
| 개발자 | 재작업·디버깅 시간 | **크게 감소** — 결함을 머지 전으로 shift-left |
| 개발자 | 리뷰 왕복 | 감소 — Critic이 1차 결함 선차단 |
| 개발자 | **유효 처리량 종합** | **1.2~1.8배** |
| 테스터 | QA로 새는 자명한 버그 | **30~60% 감소** |
| 테스터 | 버그→수정→재검증 왕복 | 감소 |
| 테스터 | 진짜 리스크에 쓰는 시간 비중 | 증가 (잡버그 노이즈 감소) |

> **대체되지 않는 것**: 실제 E2E·탐색적 테스트는 여전히 사람 몫. 루프는 노이즈를 줄일 뿐이다.

### 값이 양수인 구간 vs 음수인 구간

- **양수** — 중~대규모 변경, 검증 비용이 큰 코드(결제·인증·마이그레이션), 한 컨텍스트를 넘는 작업.
- **음수** — 1~2 파일 버그 수정·오타·문서 갱신. 게이트 왕복 비용 > 이득. → CLAUDE.md의 **파이프라인 스킵 조건**이 이 손실 구간을 이미 방어한다.

### 정직 고지

1. 위 배율은 **추정치지 측정값이 아니다.** 확신 가능한 건 *방향*(속도↓·재작업↓·새는결함↓)이지 *배율*이 아니다.
2. **토큰/비용은 확실히 증가한다** (에이전트 N개 + 검증 라운드). "재작업으로 태울 비용을 앞당겨 지불"하는 트레이드다.

### 실제 기대값을 알려면 — 이 4개를 계측한다

| 지표 | 정의 | 기대 방향 |
| --- | --- | --- |
