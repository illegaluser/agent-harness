# 멀티 에이전트 하네스 — 오케스트레이션 (L2)

이 문서는 [`01-roles.md`](01-roles.md)의 역할들을 **언제·어떤 순서로·어떻게 잇는지** 정의한다. 오케스트레이션이 책임지는 것: **게이트, 패턴 선택, effort·인스턴스 오버라이드, 실행 매핑.**

- **역할(L1)은 "누가"를, 오케스트레이션(L2)은 "언제·어떻게 연결하나"를 정한다.** 같은 역할이라도 패턴에 따라 1개로 쓰이거나 N개로 복제된다.
- **병렬은 목적이 아니라 수단이다.** 빠르려고가 아니라 *품질(독립 관점)* 또는 *확장(컨텍스트 초과)* 을 위해 쓴다.

---

## O0. 게이트 메커니즘 (공통)

게이트 = **통과 못 하면 다음으로 못 가는 조건.** 하네스의 품질·재현성은 전부 게이트로 강제된다. 3종류가 있다.

| 게이트 | 위치 | 통과 조건 | 실패 시 |
| --- | --- | --- | --- |
| **핸드오프 게이트** | 역할 간 모든 화살표 | 산출물 계약의 필수 필드가 다 찼는가 | 이전 역할에 보완 요청 |
| **승인 게이트** | Architect → Maker | 사용자의 명시 승인 | 대기. 승인 없이 진행 금지 |
| **검증 게이트** | Critic → 완료 | Critic 판정이 PASS | 아래 재호출 정책 |

### 승인 게이트 집행 메커니즘

승인 게이트는 별도 훅이나 상태 마커 파일로 집행하지 않는다. 두 축으로 성립한다.

- 사용자 대면 승인 — 메인 세션 Plan Mode의 ExitPlanMode 팝업이 1차 표면(AskUserQuestion·대화 승인 fallback). 공식 규칙상 어떤 에이전트 메시지도 승인이 아니므로 승인은 반드시 메인 세션(오케스트레이터)에서 일어난다.
- 집행 — 오케스트레이터는 승인이 성립하기 전에는 Maker를 소환하지 않는다(O4.1 수동 파이프라인의 순서 규율). 서브에이전트는 기본적으로 ExitPlanMode를 호출할 수 없으므로, 게이트는 Maker 내부가 아니라 오케스트레이터 경계에서 시퀀싱으로 닫힌다. Maker는 승인된 계획 없이 시작하면 자기신고(PLAN_CHECK)로 멈춘다.

### 검증 게이트 재호출 정책

```text
Critic 판정 ─┬─ PASS        ─▶ 완료
             ├─ CONDITIONAL ─▶ 경고 목록을 사용자에게. 처리 여부는 사용자 결정
             └─ FAIL        ─▶ Maker 재호출 (누적 최대 N회, 기본 N=2)
                                 └─ N회 초과도 FAIL ─▶ 사용자 에스컬레이션
```

- 재호출 시 Maker에게 **Critic 판정 보고 전체**를 입력으로 준다(무엇이 왜 FAIL인지).
- 불변식: 재호출돼도 **Maker ≠ Critic**. 같은 변경을 만든 Maker가 자기 검증을 겸하지 않는다.
- **팬아웃 검증 시**: 검증 게이트가 소비하는 판정은 **Referee 종합 판정**이다. 누적 최대 2회 재호출은 **Referee 종합 FAIL** 을 기준으로 증가한다 — 개별 Critic 하나의 FAIL 은 Referee의 입력일 뿐 재호출 트리거가 아니다.

### 의사결정 로그 (Decision Log)

게이트는 결정이 확정되는 지점이다. **그 결정을 대화에 흘려보내지 않고 append-only 로그에 기록한다.**

#### 오케스트레이터 — B1 정의

이 로그를 쓰는 주체는 파이프라인을 모는 **오케스트레이터**다(수동이면 메인 세션, 자동이면 Workflow 스크립트). 00-definition B2의 5원형에는 넣지 않는다 — 오케스트레이터는 "작업을 수행하는 역할"이 아니라 역할들을 잇는 **게이트 자체**이기 때문이다(01-roles R5 뒤 포인터 참조). 대신 00-definition B1의 5칸 템플릿으로 여기서 직접 정의한다.

- **책임** — 승인·검증 게이트 통과 시 그 결정을 `docs/DECISIONS.md`에 append-only로 기록하는 단 하나의 결과물(`D-NNN` 항목 또는 skip 마커)
- **입력 ←** 승인 게이트·검증 게이트의 판정 결과(무엇을·누가·왜 결정했는지)
- **출력 →** `docs/DECISIONS.md`에 추가된 `D-NNN` 항목 1개, 또는 `DECISION_LOG: skip — <사유>`
- **권한** — `docs/DECISIONS.md`에 **append만**. 다른 파일 write는 하지 않는다 — 코드·문서 변경은 여전히 Maker의 몫
- **경계** — append 외 편집(기존 `D-NNN` 항목 개정) 금지. 마커 없이 게이트를 닫지 않는다

> **00-definition C4 불변식1과의 관계** — "write는 오직 Maker만 한다"는 *작업 산출물(코드·설정 변경)* 에 대한 불변식이다. `docs/DECISIONS.md`는 작업 산출물이 아니라 **하네스 자체의 감사 로그**(누가 언제 무엇을 왜 결정했는지)이므로, 오케스트레이터의 append는 이 불변식의 **명시적 예외**로 둔다(00-definition C4 참조). 이 예외는 append 동작에만 적용되고, 기존 항목 edit에는 적용되지 않는다 — 오케스트레이터도 기존 `D-NNN` 항목은 고칠 수 없다.

#### DECISION_LOG 강제 마커

`REPO_FACTS_LOADED`와 동형의 자기신고 강제다. 오케스트레이터는 **승인 게이트·검증 게이트를 닫을 때마다** 아래 한 줄을 출력한다. **이 마커 없이는 게이트가 닫힌 것으로 치지 않는다** — 마커 자체가 게이트 종료 조건이다.

```text
DECISION_LOG: D-NNN appended
DECISION_LOG: skip — <사유>
```

- `appended` — `docs/DECISIONS.md`에 새 `D-NNN` 항목을 실제로 덧붙였을 때.
- `skip — <사유>` — 이번 게이트 통과가 새 결정을 만들지 않았을 때. `<사유>`는 아래 3개로 한정한다.

| 사유 | 뜻 |
| --- | --- |
| `no-new-decision` | 게이트는 통과했지만 이전 계획·결정과 동일해 새로 기록할 게 없음 |
| `duplicate` | 이미 기록된 `D-NNN`과 같은 결정의 재확인 |
| `pipeline-skipped` | 파이프라인 자체가 스킵된 소규모 작업(CLAUDE.md 스킵 조건) — 게이트가 없어 로그할 대상이 없음 |

- **트리거** — **승인 게이트**와 **검증 게이트**의 결과는 항상 기록(또는 skip 마커)한다. 핸드오프 게이트는 기계적 검사라 정상 통과는 기록하지 않고 **차단(필드 누락)될 때만** 기록한다.
- **성격** — append-only·불변. 한 번 쓴 항목은 고치지 않는다(ADR과 같은 계열). 이 점이 L5 메모리(덮어쓰는 "최신 사실")와 다르다 — 로그는 지워지지 않는 "왜".
- **위치** — 프로젝트당 단일 누적 파일. 기본 `docs/DECISIONS.md`(03-adoption에서 오버라이드 가능).

#### 항목 스키마 — 국·영문 병기

서사 필드(맥락·결정·대안·기각·사유)는 **EN 단락 → KO 단락** 두 줄로 병기한다. 열거·경로 필드(게이트·결정자·연결)는 **라벨만 병기**하고 값은 language-neutral(고정 토큰·경로·날짜)로 남긴다 — 매번 번역할 서사가 없어서다.

```text
## D-NNN · <Title EN / 제목 KO> — <YYYY-MM-DD>
- 게이트 (Gate): 승인 | 검증 | 핸드오프(차단 시) (Approval | Verification | Handoff-on-block)
- 맥락 (Context):
  EN: <what needed to be decided>
  KO: <무엇을 결정해야 했나>
- 결정 (Decision):
  EN: <what was decided>
  KO: <무엇으로 정했나>
- 대안·기각 (Alternatives · Rejected):
  EN: <what was excluded and why>
  KO: <무엇을 왜 뺐나>
- 사유 (Rationale):
  EN: <grounds>
  KO: <근거>
- 결정자 (Decider): 사용자 | Architect | Critic (User | Architect | Critic)
- 연결 (Links): 관련 계획서 / PR / 커밋 / [[memory]]
```

`D-NNN`은 파일 내 순번(001부터). 새 항목은 파일 끝에 덧붙인다. **D-001·D-002는 이 병기 스키마 도입(2026-07-11) 이전 항목이라 소급 개정하지 않는다**(append-only 원칙) — `docs/DECISIONS.md` 헤더에 "D-003부터 병기" 주석으로 표기한다.

## O1. 패턴 카탈로그

4개 패턴. 각 패턴은 동일 구조로 기술한다: **목적 → 발동 조건 → 구성 → 절차 → effort·인스턴스 → 실행 매핑.**

### O1.1 순차 게이트 (Sequential + Gate) — 기본형

**목적** 재현성 최우선. 하네스의 기본 흐름. 다른 패턴은 이걸 확장한 것이다.

**발동 조건** 기본값. 아래 특수 패턴의 발동 조건에 해당하지 않는 모든 파이프라인 작업.

**구성**

```text
Scout ──▶ Architect ──▶〔승인 게이트〕──▶ Maker ──▶ Critic ──▶〔검증 게이트〕
 (RO)      (RO)          사용자 승인        (RW)      (RO)
```

**절차**

1. Scout 1개 실행 → 사실 지도.
2. Architect 1개 실행 → 실행 계획.
3. **승인 게이트** — 계획을 사용자에게 제시, 명시 승인 대기.
4. Maker 1개 실행 → 변경 + 요약.
5. Critic 1개 실행 → 판정 보고.
6. **검증 게이트** — O0 재호출 정책 적용.

**effort·인스턴스** 각 역할 기본값(01-roles R7). 모두 단일 인스턴스.

**실행 매핑** 수동 파이프라인(O4.1). Agent 순차 호출 + 사용자 승인.

---

### O1.2 팬아웃-검증 (Fan-out → Verify)

**목적** 품질 강화. 한 검증을 여러 독립 관점에 맡겨 결함 적발률을 올린다. *깊이(depth)보다 다양성(diversity)* 이 버그를 더 잡는다는 원리.

**발동 조건**

- **런타임 표면 있는 코드 변경(문서·주석·순수 리네임 제외)이 파이프라인 발동 대상이면 기본값** — 코드 품질은 단일 검증이 아니라 독립 다양성 검증으로 지킨다.
- 고위험 코드 — 결제·인증·데이터 정합성·마이그레이션·보안 경계. 이 경우 팬아웃-검증에 **O1.4 적대적 검증을 중첩**한다(각 Critic이 "반증하라" 태도로 전환, effort는 `high`(고위험이면 `max`)).
- 되돌리기 비싼 변경.
- 사용자가 "철저히 검증" 명시.

**구성**

```text
... Maker(단일, 병렬 복제 안 함) ──▶ Critic ×N (독립·병렬, 렌즈 분산) ──▶ Referee (다수결·근거가중) ──▶〔검증 게이트〕
```

**절차**

1. 순차 게이트대로 Maker까지 진행. **Maker는 이 패턴에서 병렬 복제 대상이 아니다** — 팬아웃되는 것은 오직 Critic이다. write는 항상 1개 인스턴스로 남는다(00-definition C4 불변식 1 "write는 오직 Maker만" 보호). Maker를 여러 인스턴스로 나누는 것은 O1.3 분할-정복에서 worktree 격리 하에만 예외적으로 허용된다.
2. Critic을 N개(기본 3) **독립·병렬**로 복제. 각 인스턴스는 서로의 결과를 모른다.
   - **기본 구성이 렌즈 분산이다** — 동일 클론 ×3이 아니라 정확성 / 보안 / 회귀 각 1명이 기본값. "다양성을 위해 분산할 수 있다"가 아니라, N=3이 발동하면 기본으로 이 3렌즈가 배정된다. 프로젝트가 다른 렌즈 조합을 쓰려면 CLAUDE.md에 명시해야 한다.
3. Referee가 N개 판정을 종합 — 근거의 질로 가중한 다수결. 소수라도 결정적 재현 경로를 대면 채택.
4. Referee의 종합 판정으로 검증 게이트 진입.

**effort·인스턴스** Critic `high` **×N** (max 1개보다 high 여럿이 우세). Referee `high` ×1.

**비용** Critic 단일 순차 게이트 대비 약 **N배**(기본 N=3이면 ~3배) 토큰 — Critic 인스턴스가 늘어난 만큼 그대로 배가된다(Referee 종합 1회분은 상수 추가). 그래서 발동 조건을 런타임 표면·고위험으로 좁혀 놨다: 순수 문서·주석·리네임 변경은 O1.1 순차 게이트(단일 Critic)로 남겨 이 배율을 물지 않는다(O2 선택 가이드).

**실행 매핑** Workflow(O4.2) — `parallel()`로 Critic 팬아웃, Referee로 종합.

### O1.3 분할-정복 (Partition)

**목적** 컨텍스트 확장. 한 컨텍스트에 안 들어가는 크기의 작업을 조각내 병렬 처리.

**발동 조건**

- 대규모 마이그레이션·일괄 변경(수십 파일 이상).
- 광범위 감사·조사(전 코드베이스 스윕).
- 단일 세션 컨텍스트를 초과하는 작업.

**구성**

```text
Architect(분할 계획) ──▶ Maker ×M (조각별·병렬, worktree 격리) ──▶ Referee(병합) ──▶ Critic
```

**절차**

1. Architect가 작업을 **독립 조각 M개**로 분할하는 계획을 낸다. 조각 간 의존이 없어야 병렬 가능.
2. 승인 게이트.
3. Maker를 조각마다 복제, 병렬 실행. 파일 충돌 위험이 있으면 **worktree 격리**.
4. Referee가 조각 결과를 모순 없이 병합. 경계 충돌은 사유 기록과 함께 해소.
5. 병합 결과를 Critic이 **전체 단위로** 검증(조각별 검증은 통합 결함을 놓친다).

**effort·인스턴스** Maker `medium` **×M**. Architect·Referee·Critic 기본값 ×1.

**실행 매핑** Workflow(O4.2) — `pipeline()`으로 조각 파이프라인, Maker에 `isolation:'worktree'`.

### O1.4 적대적 검증 (Adversarial Verify)

**목적** 품질의 최후 방어선. 통과를 증명하는 게 아니라 **반증을 시도**해, 그럴듯하지만 틀린 결과가 살아남는 걸 막는다.

**발동 조건**

- 팬아웃-검증에서 발견된 결함의 **진위 확정**이 필요할 때.
- 결과가 그럴듯한데 확신이 안 설 때.
- 놓치면 치명적인 판정(보안·데이터 손실).

**구성**

```text
후보 결과 ──▶ Critic(반증자) ×N ──▶ 과반이 반증 실패 ─▶ 생존(확정)
                                   과반이 반증 성공 ─▶ 기각
```

**절차**

1. 검증할 후보(변경 또는 이전 Critic의 발견)를 잡는다.
2. Critic N개에게 **"이 결과를 반증하라"** 고 지시 — 기본 태도를 "refuted=true, 반증 실패 시에만 통과"로 뒤집는다.
3. 과반이 반증에 실패하면(=깨지 못하면) 생존·확정. 과반이 반증하면 기각.

**effort·인스턴스** Critic `high`(고위험이면 `max`) ×N. 다른 패턴의 검증 단계에 *중첩*해 쓴다.

**실행 매핑** Workflow(O4.2) — `parallel()` 반증자 투표.

## O3. effort·인스턴스 오버라이드 규칙

역할 기본 effort(01-roles R7)를 **패턴·리스크에 따라 오버라이드**하는 트리거. L1은 기본값, 여기가 조절 지점이다.

| 트리거 | 오버라이드 | 왜 |
| --- | --- | --- |
| 아키텍처 변경 · blast radius 큼 | **Architect → xhigh** | 설계 실수가 하류 전체로 전파. 단발 실행이라 ROI 높음 |
| 코드 변경 검증(기본) | **Critic → 팬아웃 high×3** (max 단일 아님) | 버그 사냥은 깊이보다 다양성. high 여럿 > max 하나 |
| 진위 확정 치명적 | **Critic → 적대적 검증 high(고위험 max)×N** | 반증으로 그럴듯한 오류 제거 |
| 대규모 분할 | **Maker medium ×M** | 조각별 병렬. effort는 기본, 인스턴스만 확장 |
| 저위험·기계적 조각 | **effort 하향(low)** | 명백한 작업에 깊은 추론은 낭비 |

**두 축을 구분하라:**

- **effort 축** — *한 인스턴스가 얼마나 깊게 생각하나.* 개방형·설계 문제에 올린다(Architect).
- **인스턴스 축** — *몇 개의 독립 관점을 두나.* 탐색·검증 문제에 늘린다(Critic 팬아웃).

품질 문제 대부분은 **effort를 올리기 전에 인스턴스(다양성)를 늘리는 게** 더 효과적이다.

## O4. 실행 매핑 — 하네스를 실제로 어떻게 돌리나

패턴을 이 환경의 실행 수단에 대응시킨다.

### O4.1 수동 파이프라인 (Agent 순차 호출)

**대상** 순차 게이트(O1.1) — 승인 게이트에 사람이 끼는 기본 흐름.

- `Agent` 툴로 역할을 순서대로 호출: Scout → Architect →〔사용자 승인〕→ Maker → Critic.
- 승인 게이트가 **사람의 개입을 요구**하므로 완전 자동화하지 않는다. 이게 기본형이 수동인 이유.
- 기존 CLAUDE.md의 planner→implementer→verifier 절차가 이 매핑의 현행 구현이다.

### O4.2 자동 오케스트레이션 (Workflow)

**대상** 팬아웃·분할·적대적 검증(O1.2–O1.4) — 병렬·반복이 있는 흐름.

- `Workflow` 툴로 결정적 오케스트레이션: `parallel()`(팬아웃/투표), `pipeline()`(조각 파이프라인).
- Critic/Referee의 산출물 계약은 Workflow의 `schema` 옵션으로 강제 → 파싱 없이 검증된 객체 반환.
- 파일을 병렬 변경하는 Maker는 `isolation:'worktree'`로 충돌 방지.
- **비용·opt-in 주의** — Workflow는 에이전트를 다수 소환한다. 사용자 명시 요청 시에만 가동(00-definition 부록3의 토큰 비용 고지와 연결).

### 선택 규칙

| | 수동(O4.1) | 자동(O4.2) |
| --- | --- | --- |
| 사람 승인 게이트 있음 | ✅ | — |
| 병렬·반복 없음 | ✅ | — |
| 팬아웃·분할·투표 | — | ✅ |
| 컨텍스트 초과 작업 | — | ✅ |
