# 멀티 에이전트 하네스 — 도입 (Adoption)

이 문서는 [`00`](00-definition.md)–[`02`](02-orchestration.md)에서 정의한 하네스를 **모든 프로젝트에 실제로 배치**하는 규칙이다. 핵심 질문: *무엇을 글로벌에 한 번 두고, 무엇을 프로젝트마다 덮어쓰나.*

- **도입 = 5층(L1–L5)을 "글로벌 기본값 + 프로젝트 오버라이드"로 채우는 일**(00-definition A3).
- 원칙: **한 번 정의하고 어디서나 상속, 프로젝트는 필요한 것만 덮어쓴다.** 프로젝트마다 하네스를 재발명하지 않는다.

---

## A0. 배치 원칙 — 2계층

하네스는 두 계층에 나눠 배치한다.

| 계층 | 위치 | 역할 |
| --- | --- | --- |
| **글로벌** | `~/.claude/` | 모든 프로젝트가 상속하는 **기본값** |
| **프로젝트** | `<repo>/.claude/` | 그 프로젝트만의 **오버라이드·추가** |

**우선순위: 프로젝트가 글로벌을 이긴다.** 같은 이름의 정의가 양쪽에 있으면 프로젝트 것이 적용된다. 프로젝트에 없으면 글로벌 기본값으로 떨어진다(fallback).

---

## A1. 글로벌 층 (`~/.claude/`)

모든 프로젝트가 공유하는 하네스의 뼈대. 한 번만 둔다.

### A1.1 역할 정의 — `~/.claude/agents/`

[`01-roles.md`](01-roles.md)의 5원형을 각각 한 파일로. 프론트매터는 01-roles R7 골격을 따른다.

```text
~/.claude/agents/
  scout.md       # R1  — read-only, effort low–medium
  architect.md   # R2  — read-only, effort high
  maker.md       # R3  — read/write, effort medium
  critic.md      # R4  — read-only, effort high
  referee.md     # R5  — read-only, effort high
```

각 파일 본문 = **R0 공통 규범 + 해당 역할 시스템 프롬프트**(01-roles의 프롬프트 블록 그대로).

### A1.2 글로벌 규칙 — `~/.claude/CLAUDE.md`

전 프로젝트 공통 룰. 하네스 관련으로 담을 것:

- **파이프라인 발동/스킵 조건** — 어떤 작업에 하네스를 돌리고 어떤 작업은 직접 처리하나(O2 선택 가이드 + 스킵 우선).
- **R0.3 글로벌 룰** — lint, 구독형 LLM 금지, PR/머지는 요청 시, `--no-verify` 금지, 커밋 메시지 규약(한글·영문 병기 — 형식·예시의 정본은 이 파일이다).
- **역할 경계 요약** — Maker만 write, Maker ≠ Critic 등 불변식(00-definition C4).

> 현재 `~/.claude/CLAUDE.md`에 이미 planner/implementer/verifier 파이프라인 규칙이 있다. 마이그레이션(A4)에서 이를 5원형 기준으로 갱신한다.

### A1.3 메모리 — `~/.claude/.../memory/` (L5)

세션 간 지속 사실. 하네스가 새로 만드는 게 아니라 기존 메모리 체계를 그대로 쓴다(00-definition C5).

---

## A2. 프로젝트 층 (`<repo>/.claude/`)

프로젝트는 **필요한 것만** 덮어쓴다. 아무것도 안 두면 글로벌 기본값으로 완전히 동작한다.

### A2.1 역할 오버라이드 — `<repo>/.claude/agents/`

- 같은 이름(`critic.md` 등)을 두면 **그 프로젝트에서 글로벌을 대체**한다.
- 흔한 오버라이드: 프로젝트 특화 검증 항목을 Critic에, 도메인 지식을 Scout에, 도구 권한 조정.
- **주의** — 오버라이드는 전체 교체다. 글로벌 R0 규범이 필요하면 프로젝트 파일에도 상속해야 한다. 소폭 변경이면 오버라이드보다 아래 CLAUDE.md 추가가 낫다.

### A2.2 프로젝트 규칙 — `<repo>/.claude/CLAUDE.md`

역할 파일을 통째로 갈아끼우지 않고 **규칙만 얹는** 경로. 하네스는 이걸 1순위 소스로 읽는다(R0.2).

- **프로젝트 NON-NEGOTIABLE 룰** — launcher 강제, 토폴로지 분리, 포트 규약, 버전 핀, 외부 시스템 등록 경로 등. Architect가 계획에 반드시 반영.
- **추가 발동 카테고리** — 이 프로젝트에서 하네스를 꼭 돌려야 하는 작업 유형.
- **패턴 튜닝** — 예: "이 저장소의 결제 모듈 변경은 항상 팬아웃-검증(O1.2)" 같은 프로젝트별 라우팅.

---

## A3. 우선순위 규칙 (Precedence)

충돌 시 누가 이기나. 위일수록 강하다.

```text
1. 프로젝트 CLAUDE.md의 NON-NEGOTIABLE 룰      ← 최강
2. 프로젝트 .claude/agents/ 오버라이드
3. 글로벌 ~/.claude/CLAUDE.md 규칙
4. 글로벌 ~/.claude/agents/ 기본 역할 정의       ← 기본값
```

- **불변식은 프로젝트가 못 뒤집는다.** 00-definition C4의 불변식(Maker만 write, Maker≠Critic, 게이트 없는 전이 금지)은 프로젝트 규칙보다 위다. 프로젝트는 *조일* 수는 있어도 *풀* 수는 없다.

---

## A4. 기존 3-에이전트에서 마이그레이션

현재 `~/.claude/agents/`에 planner/implementer/verifier가 있다. 5원형으로 전환하는 순서.

| 단계 | 작업 |
| --- | --- |
| 1 | `planner.md` → `architect.md`로 대체 (01-roles R2 프롬프트로 갱신) |
| 2 | `implementer.md` → `maker.md` (R3, PR/머지 요청 시 수행 반영) |
| 3 | `verifier.md` → `critic.md` (R4, 적대적 검증 태도 강화) |
| 4 | `scout.md`, `referee.md` **신규 추가** (R1, R5) |
| 5 | 세 기존 파일에 흩어진 글로벌 룰을 **R0.3으로 통합**, 중복 제거 |
| 6 | `~/.claude/CLAUDE.md`의 파이프라인 절차를 5원형·4패턴 기준으로 갱신 |

- **하위 호환** — 기존 planner→architect 등 매핑이 1:1이라, 기존 워크플로우는 이름만 바뀌고 그대로 동작한다(00-definition 부록1).
- **점진 전환 가능** — Scout/Referee 없이 architect/maker/critic 3개만으로도 순차 게이트(O1.1)는 완전 동작. 팬아웃·분할이 필요해질 때 Referee를 붙인다.

## A5. 프로젝트 도입 체크리스트

새 프로젝트에 하네스를 켤 때. **대부분 아무것도 안 해도 된다** — 글로벌이 기본 동작하므로.

- [ ] 이 프로젝트에 **프로젝트별 NON-NEGOTIABLE 룰**이 있나? → `<repo>/.claude/CLAUDE.md`에 명시.
- [ ] 글로벌 역할로 **부족한 도메인 검증·지식**이 있나? → 해당 역할만 `<repo>/.claude/agents/`로 오버라이드.
- [ ] 특정 모듈에 **강제할 패턴**이 있나(예: 결제=팬아웃)? → CLAUDE.md에 라우팅 규칙.
- [ ] **의사결정 로그 위치**를 기본(`docs/DECISIONS.md`)에서 바꿀 건가? → 바꿀 때만 `<repo>/.claude/CLAUDE.md`에 경로 명시.
- [ ] 위 넷 다 아니오 → **설정 없이 글로벌 기본값으로 사용.**

---

## A6. 무엇이 글로벌이고 무엇이 프로젝트인가 (요약)

| 항목 | 글로벌 기본 | 프로젝트 오버라이드 |
| --- | --- | --- |
| 역할 원형(5개) | ✅ 정의 | 도메인 특화만 |
| R0 공통 규범 | ✅ | (상속) |
| 불변식(C4) | ✅ 강제 | 조이기만 가능, 풀기 불가 |
| 파이프라인 발동/스킵 | ✅ 기본 | 카테고리 추가 |
| 패턴 라우팅 | 일반 규칙 | 모듈별 강제 |
| NON-NEGOTIABLE 룰 | — | ✅ 프로젝트 소유 |
| effort 기본값 | ✅ | 필요 시 조정 |
| 의사결정 로그(C6) 위치 | ✅ `docs/DECISIONS.md` | 경로만 변경 가능 |

## A7. 도입 이후 — 검증

배치가 끝나면 하네스가 실제로 의도대로 도는지 확인한다.

- **경계 테스트** — Maker에게 계획 없이 시작을 시켜보고 멈추는가? Critic에게 자기 변경 검증을 시켜보고 거부하는가?
- **게이트 테스트** — 승인 없이 Maker가 진행하지 않는가? Critic FAIL 시 재호출되는가?
- **기대 효과 계측** — 00-definition 부록3의 4지표(escaped defect / rework ratio / cycle time / 토큰)를 도입 전후로 비교.

> 이 문서(`00`–`03`)로 하네스의 **정의·역할·오케스트레이션·도입**이 모두 닫혔다. 실제 파일 생성(A1.1의 5개 agent 파일, A4 마이그레이션)은 이 스펙을 구현하는 별도 실행 단계다.
