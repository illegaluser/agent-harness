## 커밋 메시지 규약 — 한글·영문 병기

모든 커밋 메시지는 **한글과 영문을 병기**한다. 한국어가 먼저이고(비개발자 독자 기준), 영문은 같은 내용을 옮긴 것이다.

- **제목** — `<type>: <한국어 요약> / <English summary>`. 슬래시 하나(` / `)로 병기한다. `<type>` 은 저장소의 기존 관례(`feat` / `fix` / `docs` / `refactor` / `chore` 등)를 따른다.
- **본문** — 한국어 항목 블록을 먼저 쓰고, `[EN]` 한 줄을 구분자로 둔 뒤, 같은 항목을 같은 순서로 영문 블록에 쓴다. 두 블록의 항목 수와 순서는 1:1 로 대응한다.
- **문체** — 한국어는 비개발자도 이해할 쉬운 말. 영문은 같은 내용을 영어권 커밋 관례(명령형 현재시제)로 옮긴다.
- **본문이 한 줄이면** 블록을 나누지 않고 `한국어 문장 / English sentence` 한 줄 병기로 갈음할 수 있다.
- **구분자로 `---` 를 쓰지 않는다** — `git format-patch` / `git am` 이 `---` 로 시작하는 줄을 패치 경계로 보고 그 뒤(영문 블록 전체)를 잘라낸다. 그래서 `[EN]` 을 쓴다.
- **`Co-Authored-By` trailer 금지.** 다른 trailer 도 사용자가 명시 요청할 때만 붙인다.

예시:

```text
docs: 하네스 커밋 규약 추가 / Add harness commit convention

- 5개 에이전트 정의의 커밋 규칙을 병기로 통일
- 전역 CLAUDE.md에 동일 규칙 추가

[EN]

- Unify commit rules across 5 agent definitions
- Add the same rule to the global CLAUDE.md
```

## Subagent 위임 규칙 — Scout → Architect → Maker → Critic

> **스펙 출처: 하네스가 설치된 프로젝트의 [`harness/CORE.md`](harness/CORE.md) 하나다.**
> 정본 저장소는 `~/Developer/agent-harness` 이고, 설치는 `bash harness/install.sh <프로젝트경로>`,
> 제거는 `bash harness/install.sh --uninstall <프로젝트경로>` 다.
> **아래 내용과 `CORE.md` 가 어긋나면 `CORE.md` 가 이긴다.** 이 문서는 사본이지 정본이 아니다.

`~/.claude/agents/` 에 **scout / architect / maker / critic / referee** 다섯 글로벌 subagent 정의가
있고, 내용은 `agent-harness` 저장소의 `harness/agents/*.md` 와 동일하다. 프로젝트가 자기
`.claude/agents/` 에 같은 이름으로 정의를 두면 그 프로젝트에서는 project-level 이 우선 적용된다.

### 하네스가 깔려 있는가 — 먼저 확인한다

`기계`/`조언` 구분이 여기 달려 있다. 판정 절차:

1. 프로젝트 루트에 `.claude/harness.json` 이 있고 `enforce` 가 `true` 인지 본다.
2. `true` 면 아래 `기계` 규칙을 **훅이 실제로 막는다.** 어길 수 없다.
3. 파일이 없거나 `enforce` 가 `false` 면 **아래 전부가 `조언` 이다.** 아무것도 막히지 않는다.
   그 상태에서 "게이트가 막을 것이다"를 전제로 행동하지 마라 — 안 막는다.

- **금지 예:** 하네스 없는 프로젝트에서 산출물 5개를 직접 고치고 "게이트가 안 막았으니 괜찮다"고
  판단한다. 거기엔 게이트가 없다. 규칙을 스스로 지켜야 한다.
- **허용 예:** 하네스 없는 프로젝트에서 3개째 파일을 고치기 전에 계획을 제시하고 승인을 받는다.

### 훅이 실제로 막는 것 4가지 (`기계`, 하네스 설치 시)

| 걸리는 일 | 결과 |
| --- | --- |
| 메인 스레드가 한 턴에 산출물 파일을 `main_thread_file_limit`(기본 2) 개 넘게 수정 | `PreToolUse` 차단 |
| 메인 스레드가 Bash(`sed -i`·`perl -i`·리다이렉트·`tee`·`rm`·`rmdir`·`cp`·`mv`·`install`)로 산출물 수정 | 차단 |
| 수락된 `ExitPlanMode` 없이 `maker` 스폰 | 차단 |
| 위임이 일어난 턴에 검증자(`critic`) 없이 종료 | `Stop` 차단, `max_close_blocks` 회 후 통과 |

**막히면 우회하지 말고 규칙대로 하라.** 게이트가 잘못됐다고 판단되면 `.claude/harness.json` 에서
끄고 **그 사실을 사용자에게 보고한다** — 조용히 우회하는 것이 이 하네스가 막으려는 바로 그 행동이다.

Bash 차단에는 **알려진 미탐이 있다.** 목록은 `harness/hooks/gate.py` 의 `bash_targets` docstring 에
있고, 미탐이 있다고 해서 우회해도 되는 것은 아니다.

### 자동 파이프라인이 발동하는 카테고리 (`조언`)

훅은 이 카테고리를 판정하지 않는다 — 파일 개수만 센다. 아래는 스스로 지켜야 하는 판단이다.

다음 중 **하나라도 해당하면** Scout → Architect → (사용자 승인) → Maker → Critic 순서로 진행한다.

- 신규 모듈/패키지 추가 또는 기존 모듈의 아키텍처 변경
- 신규 테스트 슈트 추가 (특히 e2e / integration)
- `build.sh` / launcher / CI / 배포 / git hook 스크립트 수정
- **하네스 자체 수정** (`harness/hooks/gate.py` · `harness/install.sh` · `harness/CORE.md` ·
  `harness/agents/*.md` · `~/.claude/agents/*.md` · 이 파일의 `HARNESS` 블록)
- 실행 토폴로지 변경 (host ↔ container ↔ VM ↔ remote)
- 외부 시스템 (DB, MQ, LLM provider, vector store 등) 연동 흐름 수정
- 의존성 버전 핀 변경 (보안 / 호환성 영향이 있는 것)
- 보안/약관 영향이 있는 변경 (인증·인가, 외부 LLM 호출 경로 등)
- 프로젝트 `CLAUDE.md` 가 추가로 지정한 카테고리

### 파이프라인을 건너뛰는 케이스 (직접 처리)

- 1~2 개 파일의 명확한 버그 수정 / 오타 / 문서 단순 갱신
- 사용자가 이미 구체적 코드 변경 위치/내용을 지시한 경우
- lint 만 정리하는 작업
- 단, 위 경우에도 변경 후 critic 단독 호출은 **권장** (사용자가 빠르게 끝내라고 명시한 경우 면제)

### 기계적 변경 — Architect 생략

**단일 정의된 변환을 N개 파일에 적용하고 설계 판단이 없으면**, 파일 개수와 무관하게 Architect 를
생략한다: `@agent-scout` → `@agent-maker` → `@agent-critic`.

기계적 변경의 조건 (전부 충족):

- 변환 규칙이 한 문장으로 적히고 대상마다 동일하다 (문자열 치환, 이름 변경, 포맷 통일 등)
- 새 동작·새 인터페이스·새 의존성이 생기지 않는다
- 되돌리기가 `git revert` 한 번이다

**대상 목록이 불확실하면 Scout 를 반드시 먼저 부른다.** 사본이 몇 곳에 있는지 모르는 채로 Maker 를
부르면 누락이 난다. Scout 는 sonnet/low 라 싸다 — 여기서 아끼지 마라.

설계 판단이 하나라도 실재하면(형식 선택, 트레이드오프, 스펙 개정) 기계적 변경이 아니다. Architect 를 부른다.

**우선순위 — 카테고리 규칙이 이긴다.** 위 `자동 파이프라인이 발동하는 카테고리` 에 해당하면, 변경이
기계적이어도 Architect 를 생략하지 않는다. 예: `build.sh` 를 포함한 저장소 전역 변수명 치환은 기계적이지만
빌드 스크립트 수정이므로 전 과정을 거친다. 기계적 변경 규칙은 **카테고리에 걸리지 않는 작업**의
파일 개수 문턱을 없애는 것이지, 카테고리를 무력화하는 것이 아니다.

### 변경의 파급 범위를 먼저 적는다 (`조언`)

작업 대상 목록을 확정하기 전에 **"이 변경으로 거짓이 되는 문서·설정이 무엇인가"** 를 적는다.
삭제·이름변경·경로이동은 그것을 가리키는 모든 곳을 함께 낡게 만든다. 그 목록은 diff 밖에 있으므로
diff 를 봐서는 나오지 않는다 — 아래 `토큰 규율의 예외 2`(전수 대조)를 여기에 적용한다.

**저장소 밖도 범위다.** `~/.claude/CLAUDE.md` · `~/.claude/agents/*.md` · `~/.claude/settings.json` 은
git 밖이라 `git grep` 에 안 잡히지만 모든 세션에 주입된다. 하네스·에이전트·경로 규약을 바꾸면
**여기부터 확인한다.**

- **금지 예:** 저장소의 옛 스펙 디렉터리를 지우면서, 그 경로를 정본으로 가리키는
  `~/.claude/CLAUDE.md` 를 범위 밖으로 둔다. 모든 프로젝트가 없는 문서를 근거로 동작하게 된다.
- **허용 예:** 삭제 계획에 "이 경로를 참조하는 곳" 전수 목록(저장소 안 + `~/.claude/` 안)을 넣고,
  각각 수정·삭제·유지 중 무엇인지 파일 단위로 지정한다.

### 검증 등급 — Critic 모델 오버라이드 (`조언`)

Critic 기본은 `harness/agents/critic.md` 의 frontmatter 값(`claude-sonnet-5` / `effort: high`)이다.
다음 중 하나라도 해당하면 **`model: claude-opus-5` · `effort: xhigh`** 로 올려서 호출한다.
`critic.md` 와 같은 값이다 — 검증 여부가 아니라 **강도**를 조절하는 것이다:

- 인증·인가, 비밀정보 취급, 외부 LLM 호출 경로
- `build.sh` / CI / 배포 / git hook / launcher 스크립트 / **하네스 자체**
- 실행 토폴로지 변경, 외부 시스템(DB·MQ·vector store) 연동 흐름
- 되돌리기 비용이 큰 변경 (마이그레이션, 스키마)

### 토큰 규율 (모든 역할 공통)

- 같은 파일을 두 번 읽지 않는다. 필요한 범위만 읽는다.
- N개 파일에 같은 변환을 적용할 때는 파일별 Edit 이 아니라 **스크립트 한 번**으로 처리한다.
- diff 로 충분한 검증을 파일 전체 재독으로 하지 않는다.
- 탐색적 조회는 Scout 의 일이다. Architect / Maker / Critic 은 주어진 사실 지도 위에서 움직인다.
- 툴 호출 횟수가 곧 비용이다. 매 호출마다 대화 전체가 다시 실려 간다.

### 토큰 규율의 예외 — 절약해서는 안 되는 두 가지

위 절약 규칙은 **국소 결함**(한 줄·한 함수 안에서 판정되는 것)에만 유효하다. 아래 두 경우는
절약하면 결함을 못 잡는 것이 아니라 **결함이 없다고 잘못 보고하게 된다.** 예외 없이 적용한다.

**예외 1 — 종합 판정 전 통독.**
자신이 작성·개정한 산출물에 대해 "구현 가능" · "완료" · "이상 없음" 류의 **종합 판정**을 내리기
전에는 그 산출물을 **처음부터 끝까지 읽는다.** grep 결과·서브에이전트 요약·자기 브리프의 기억으로
판정하지 않는다. 부분 확인만 했으면 판정을 내리지 말고 **무엇을 확인했고 무엇을 안 봤는지**를
그대로 보고한다.

- **금지 예:** 2000줄 문서를 grep 과 에이전트 보고서로만 훑고 "전부 구현 가능"이라고 판정한다.
- **허용 예:** 통독하지 못했으면 "화면↔API↔스키마 3단만 확인했고 지표↔변환기 축은 안 봤다"고
  범위를 명시해 보고한다.

**예외 2 — 교차 참조는 전수 대조한다.**
한 곳이 정의한 집합을 다른 곳이 참조하는 관계(필드·식별자·절 번호·엔드포인트·컬럼)의 불일치는
**diff 밖에 있다.** 양쪽 다 이번에 안 건드렸어도 어긋나 있을 수 있다. 그러므로 "정의 집합"과
"참조 집합"을 **뽑아서 차집합을 낸다.** 이건 통독이 아니라 grep·스크립트 한 번이라 비용이 거의
없다 — 토큰 규율과 충돌하지 않는다.

- **금지 예:** 변경된 절만 읽고 "참조 깨짐 없음"이라고 판정한다.
- **허용 예:** `A절이 요구하는 필드 목록 ∖ B절이 제공하는 필드 목록` 을 스크립트로 뽑아 0건임을
  확인하고, 그 명령과 결과를 보고에 남긴다.

### 파이프라인 절차 (기본형: 순차 게이트)

1. `@agent-scout` 호출 → 사실 지도 작성 (코드베이스·문서 조사)
2. `@agent-architect` 호출 → 실행 계획 작성
3. 계획을 사용자에게 제시하고 **명시적 승인** 대기 (승인 게이트). 승인 없이 다음 단계 진행 금지.
4. `@agent-maker` 호출 → 승인된 계획으로 구현
5. `@agent-critic` 호출 → 판정 보고 (검증 게이트)
6. 판정에 따라:
   - PASS: 완료 보고
   - CONDITIONAL: WARNING 목록 사용자에게 전달, 처리 여부 결정 위임
   - FAIL: `@agent-maker` 재호출 (최대 2 회). 그래도 FAIL 이면 사용자에게 에스컬레이션.

### 오케스트레이션 패턴 (`조언`)

| 패턴 | 구성 | 발동 조건 |
| --- | --- | --- |
| **순차 게이트** | Scout→Architect→Maker→Critic | 기본형. 재현성 최우선 |
| **팬아웃-검증** | Critic ×N → `@agent-referee` 종합 | 런타임 표면 코드 변경 기본 검증 (고위험은 적대적 검증 중첩) |
| **분할-정복** | Maker ×M → `@agent-referee` 병합 → Critic | 단일 컨텍스트를 초과하는 대규모 작업 |
| **적대적 검증** | Critic ×N 에게 "반증하라" | 판정 진위 확정이 치명적일 때 다른 패턴에 중첩 |

**서브에이전트는 기본적으로 백그라운드로 띄운다.** 동기(foreground)로 걸면 그 몇 분 동안
사용자에게 진행 상황을 보고할 수 없다. 결과가 있어야 다음 판단이 서는 경우에만 동기로 건다.

### 에이전트별 경계

`기계` 로 표시된 것은 `tools:` frontmatter 가 강제하므로 어길 수 없다. 나머지는 `조언` 이다.

- scout — `기계` Write/Edit 없음. `조언` 판단·권고 금지, 사실만 보고.
- architect — `기계` Write/Edit 없음. `조언` 계획만 쓰고 코드는 안 씀.
- maker — `기계` 수락된 `ExitPlanMode` 없이 스폰 불가. `조언` 승인된 계획 없이 시작 금지.
- critic — `기계` Write/Edit 없음(자기가 만든 변경이 존재할 수 없다). `조언` 발견·판정·보고만.
- referee — `기계` Read/Glob/Grep 만. `조언` 새 작업·새 코드 생성 금지.
